## 2. Design: the hop limit
      Answer: In my design, i added 8 bit field called "hop_limit" at the end of the tunnel header. In the lab scenario, a smaller field would be enought for the 2- switch path, but i set it as 8 bit because the i want to make the header field fill with whole bytes. I put it last in the header, and "proto_id" and "dst_id" stay in the same position. The new field add one more bytes from previous one, and so total 5 bytes for the new field. I set the start values at 8 in "send.py". Currently the path is from h1 to s1 to s2 to h2 crosses 2 switches, so the value must be at least 2, else a valid packets would be dropped. I chose 8 in my lab to have more spaces if ading more path in future. The hop limit is handled in the ingress, on the tunnel branch, before myTunnel_exact is applied. The switch checks first, then subtracts. If hop_limit is 0, the packet is dropped. if not. it will subtracted by 1 and the table is applied. I check first because the field is unsigned, so subtracting from 0 would wrap around to 255 and the packet would never be dropped. With a start value of 8, a packet is forwarded 8 times and dropped on the 9th pass. The parser and deparser did not need any change, because extract and emit read and write the whole header, so they handle the new field automatically. The change I made is on the host in send.py and receive.py. Each have their own copy of the tunnel header in Scapy, so I added hop_limit there, in the same order and size as the switch (16, 16 and 8 bits). If the hosts and switches disagree about the header, the bytes are read in the wrong place, and packets are misread or dropped.

## 3. Implementation
     Answer: In tunnel.p4, I added bit<8> hop_limit to the tunnel header. Then I changed the ingress logic in the apply block. When a packet has a valid tunnel header, the switch first checks the hop limit. If it is 0, the packet is dropped. Otherwise, the switch subtracts 1 from the hop limit and then applies the table. I did not change the parser, deparser or tables, because they handle the whole header and pick up the new field by themselves. In send.py and receive.py, I changed the host side, so that the hosts use the same tunnel header as the switch. send.py builds the packet, so I added hop_limit to its tunnel header and a --hops option to set the starting value, here i set it "8". receive.py reads the packet, so I added hop_limit to its tunnel header too, and made it print the value that arrives. Then, the check for 0 comes before the subtraction on purpose. The hop limit cannot go below 0, so subtracting 1 from 0 would wrap around to 255, and the packet would never be dropped. Also, the hosts and the switch must use the same header layout (16, 16 and 8 bits), or they would read the bytes in the wrong places.

     b. First option is add version field in the header. New switches can check the version to know how to read the packet, which makes it easier to support several header versions in the same network. But an old switch does not know the field, so it would misread the packet, and I must upgrade all the switches before the new format can be used. Another option is a new EtherType for the new header, for example 0x1213. New switches understand both the old and new types. An old switch does not recognise the new type, so it drops the packet instead of misreading it. This separates the two formats clearly, but the packets are lost until the old switch is upgraded. I would choose the new EtherType because it provides safer failure behaviour. First, I would upgrade the switches one by one with a program that supports both EtherTypes. Once all switches are upgraded, I would change the hosts to send packets using the new EtherType. If problems occur, I can switch the hosts back to the old EtherType as a rollback plan.

     c. check_paths() is in control plan, it checks routing tables before packets are sent. It detects missing routes and routing loops, and identifies the faulty router. However, it cannot detect changes made after the check or problems in switch programs and tunnel tables. In data plan, the hop limit is carried inside the packet and decreases at every switch. When it reaches zero, the packet is dropped, preventing it from looping forever. It can handle loops caused by incorrect entries or live updates, but only detects them after they occur. It also only protects tunnel packets. In conclusion, both methods complement each other. Control plane protection detects and helps locate loops before traffic starts, while the hop limit stops packets that are already looping. Using both provides better protection against routing loops.

     d. The cost is very small. For each tunnel packet, the switch does only two simple things, it checks if the hop limit is 0, and it subtracts 1 from it. It does not need a new table lookup or extra memory, so it should not slow the switch down. A normal router already does the same thing with the IPv4 TTL at full speed. There are only a few small costs. Every tunnel packet gets one byte longer, because of the new field. The check may need one extra step in the switch pipeline, since it runs before the table lookup. The IPv4 checksum is not affected, because the hop limit is not part of the IPv4 header.
